All design and code so far. The assistant loop does not use the memory yet.

  • 8 Compose services on 3 internal networks with no outbound route
  • 6 SQL migrations and about 2,300 lines of Python
  • 70 test functions, and the database tests run on real Postgres
  • Full stack measured on one 8 GB server: about 3.1 GiB used, no swap

What it cost

Recall scores every row in scope. The scores stay simple to explain, but this will not hold for a large store.

  1. A worker that dies in the middle of a job never records a failure, so the job could be reclaimed forever.

    I built the queue in Postgres with SKIP LOCKED and a visibility timeout. Failures and crash reclaims have separate counters, each with its own dead-letter limit. If only one half of a job succeeds, that half is kept.

    A test on real Postgres shows a poison job dead-letters and stops being claimed.

    In the diagram: Queue table in Postgres

  2. Recall must mix vector, text and graph signals, keep low-trust and deleted rows out, and still work when the embedding model is down.

    One SQL statement filters by status and trust first, then scores. A depth-limited recursive CTE walks the graph. If the embedding call fails, the vector score is zero and the other two signals still answer.

    In the diagram: Memory service

  3. The model gave one real thing different types on different runs, so it became several entities and the graph split.

    Identity is now the normalized name only, with a unique index behind it. A migration merged the duplicates and repointed their edges. The upsert keeps the first non-null type. Homonyms merge, and I accept that for now.

    In the diagram: Graph contract

  4. The model gate crash-looped on a network with no internet, and it showed exit code 0 and empty logs.

    I found two causes: a price map fetched at import, and an OOM kill at 512 MB, because import peaks near 1 GiB. Now it uses the bundled map and a 1536 MB limit.

    In the diagram: LiteLLM gate

Personal Assistant Agent README

What it is A set of services for a private assistant. It is still in progress. It ran on one private server for acceptance runs, with no users. The last commit is from July 2026. You drive it from a shell, through its helper scripts, because it has no screen and no chat channel yet.

How it works The memory service stores entries in Postgres and finds them with both full-text and vector search. A worker reads new memories, pulls out entities and relations through a model gate, and checks them against a contract. Each graph edge points back to its source.

How it runs The services run together with Compose. The memory service speaks MCP over HTTP or stdio, but the orchestrator does not call it yet. Model calls pass through one gate, on a network with no other way to the models.
