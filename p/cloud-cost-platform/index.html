Billing files are large, they arrive late, and old months get restated in new files. The daily load had to find all of them and stay safe to run again.

Back to what was hard
  1. 1 New billing files arrive
  2. 2 The ingest job loads them in batches
  3. 3 A checked batch moves to the billing table
  4. 4 A job refreshes the rollup for the dashboards
  5. 5 A question picks a template or checked SQL

I owned the whole system: pipeline, warehouse, API, web app and deploys.

  • A large warehouse of billing rows, growing every day
  • More than a thousand automated tests, run by hand before deploys, with no CI server
  • Close to twenty numbered warehouse migrations and a few dozen dashboard templates
  • Several hundred commits, all mine except the first repo setup

What it cost

The rollup keeps only low-cardinality fields so it stays small. Questions about single resources or names still scan raw rows and stay slow.

  1. Costs on some days looked far too low, yet every layer of the system seemed correct. The provider keeps adding files to old date folders for days or weeks, and the daily run read only yesterday's folder, so a large share of files never loaded and nothing failed.

    I ran separate read-only checks, one per layer, and the service mix on bad days was the same but scaled down, which meant data was lost, not moved. The daily run now scans a rolling week, a weekly sweep covers a month, the rollup refresh windows match both, and a separate alert fires when no file has loaded recently.

    The backfill loaded every missing file with no failures, each rebuilt day matched the source, and the dips went away.

    In the diagram: Ingest job

  2. A rerun must never count a charge twice. But two real charges can look almost the same, and the warehouse removes duplicates only some time after the insert.

    There are two gates. File name plus etag in an audit table skips files already loaded. Below that, a hash over a wide set of columns ends the sort key of a ReplacingMergeTree, ingest time stays out of the key as the version, and exact readers go through a dedup view because merges run late.

    In the diagram: Audit tables

  3. Dashboard queries over a month were far too slow on a cold start, and they still had to match the deduplicated numbers.

    I measured before optimizing. Projections came out, because the optimizer never picked them. Scan volume was the real cost, so I built a daily rollup from the deduplicated source. Each day loads into staging, must match the source to the cent, and only then does REPLACE PARTITION swap it in. A day that fails stays as it was.

    In the diagram: Daily rollup

  4. The chat must never invent a number, even when the model writes the SQL.

    Known questions map to typed parameters and fixed SQL templates. Other questions get generated SQL that must parse as one SELECT on one allowed table, and it runs inside a row filter. A checker then compares every number in the answer with the query results, allows one retry, and returns an error if it still fails. An audit row is written before every model call.

    Unbacked numbers get stopped, but the chat is not finished. At the last run on record, a fixed set of test questions passed only about half, and a fix that missed the bar was reverted.
