  • Most commits are mine, my partner holds a clear share

What it cost

I replaced human review of each query with a reviewed compiler and a test corpus. It answers rankings and comparisons, but a query that runs and is silently wrong became possible, so the corpus was the last thing we would cut.

  1. People ask in free text, but a language model must not write SQL or state a number that a manager then trusts.

    The model makes one call before any data is read, and its only useful output is a small JSON intent. A validator checks it against a closed list of measures and operators, then a compiler picks a pre-written statement and binds the values. Figures come only from SQL rows, and the caption shows the intent that ran, so a wrong mapping looks like a wrong question.

    The scripted question set passed on the live service, correct refusals included. In local rehearsals every figure was compared with separate SQL, and no wrong number was served.

    In the diagram: Intent validator

  2. One order holds many lines of different types, so a plain join or count gives a number that looks right and is wrong.

    The grain rules live in the SQL and the compiler, not in a reader's memory. A count that has no clear meaning per line type returns null with a stated reason. An order is dated by its earliest line, and a test compares that SQL block byte for byte across the statements that use it. Expected test values come from hand-run queries pinned to a dataset hash, never from the compiler.

  3. The schema holds many tenants in one database, and application discipline alone would not stop one bad query from crossing between them or exposing cost data.

    Forced row-level security with a non-owner role and a tenant setting that lasts one transaction, so a missing setting returns no rows. Sensitive columns are closed by column-level grants. The audit table is append-only through grants, a trigger and policy.

    I tested this by running it: before the column grants, the application role could read the cost side. After them, the database refuses.

    In the diagram: PostgreSQL with row security

  4. The demo needed realistic data with the original structure, but the client's real records could never reach the environment or the repository.

    A seeded pipeline runs only on a private machine. It works from an allow-list, so a new unknown column stops the run, and it refuses to write to any path git does not ignore. A separate verifier reads only the output, with its own readers and arithmetic, and a failed check blocks sign-off.
