  • One user, me, by design
  • More than a dozen tables, dozens of numbered migrations
  • Several hundred automated tests, plus browser and live database checks
  • Over a hundred merged pull requests in about three months, one author

What it cost

The journal goes whole with each request, or a whole period I choose. The picture stays complete, but more private text reaches the provider and there is a hard size limit, so very long histories will need compaction.

  1. The page talks to the database directly with a public key, so row rules are the whole authorisation, and a model key must never reach the browser.

    Every table and the file bucket carry one owner-only policy, and a check script fails on a wrong policy expression or an extra policy. A small gateway seals each model key with AES-GCM under a secret only the host holds, and it reads rows with the caller's token, never a service key.

    The database alone or the host secret alone does not give up a key.

  2. A model reads a printed document, and one wrong decimal would enter my records as fact.

    The answer comes through a forced schema, then plain code checks it: the number must equal the printed text, names and units must match, a comma number waits for me, and nothing is converted. A second model call checks the same file, and if it fails nothing can be saved.

    Saved rows carry their model and source file, so generated and typed values stay apart.

  3. The pattern finding is a model reading the journal, and a model shown part of the data sounds as sure as one shown all of it.

    There is no statistics code and no retrieval. One pure function writes every table onto the line of its day, counts in code and states how many days it covers. A question changes the prompt and never the data, a test holds the text identical across questions, and I can read the exact text sent.

  4. A panel of advisers answers one question through several paid calls, and a stop or a failed call must not waste the ones already paid for.

    The first adviser runs alone so its call writes the journal to the provider cache. The rest then run together and read it, followed by a moderator and a refiner. Each reply is saved on arrival, so a resume asks only for what is missing.
