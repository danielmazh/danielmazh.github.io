The whole app: product, database, sync, screens, two languages, tests and deploy.

  • 93 commits over nine days, with no other contributors
  • 6 tables under row level security, with 12 policies
  • 165 unit tests in CI, plus 6 browser tests run locally
  • One small app: two languages, at most 500 active items per household

What it cost

Only ticks work offline. Other writes wait for the network. That avoids merge conflicts, but you cannot edit the list with no signal.

  1. Two phones can change the same stock at once, and a plain save would lose one change.

    Clients send a relative change to server functions, never a new value. Finishing a trip changes stock and clears ticks in one transaction. Settings saves carry a version, so a stale copy is refused.

    In the diagram: Postgres with row rules

  2. In a store with weak signal a tick must not get lost, and a late tick must not come back after the trip ends.

    A browser queue per household keeps the last state of each item, and only one tick request runs at a time. Network errors and expired tokens keep the change, a server refusal drops it, and finish waits until nothing is unsent.

    In the diagram: Offline tick queue

  3. The browser holds only a public key, so the rules must hold inside the database.

    Row level security checks membership on every table, and column grants close the rest. Households and members change only through functions. Composite keys block links across households, and locks keep limits true under parallel writes.

    In the diagram: Postgres with row rules

  4. An installed app can keep running an old cached build after the schema changes, and a new build can reach a database that is not migrated yet.

    Recent schema changes add columns and keep the old ones, and triggers fill the new fields, such as the keep-at-home target, for rows from old copies. The app sends a home language only for English, so Hebrew sign-ups work before that migration runs. The service worker cache is named by a build hash.

Household Shop README

What it is An installable app for one home, called Home Shopping on the phone. It works in English and Hebrew: a new device asks for the language first, and the base products come in that language. It has three tabs (home, products, settings), a shop mode and a help page.

How it works Each product has a store, the trips that buy it and how many packs to keep at home. Home shows the next trip and when the others come. You mark what you used, and a sheet shows what is left and which trip fills it back. "Go shopping" opens the list by store, ticks move to the cart, and "Done" adds them to stock. Others at home join with a code or a link sent on WhatsApp, and sign in by email with no password. Everyone sees changes live, and ticks made offline wait in a queue. For a new product, an AI helper can fill in the name, emoji, category and price, with undo.

How it runs The screens talk to one storage interface with two backends, browser only for a demo and Supabase for real shared use. The quantity math is pure code, apart from storage and screens. All text sits in one typed dictionary, so a missing English string fails the type check. Base data exists in SQL for real homes and in TypeScript for the demo, and a unit test compares them in both languages. A Cloudflare function holds the model key and checks the session. Unit tests and deploy run on GitHub Actions, and browser tests run locally.
